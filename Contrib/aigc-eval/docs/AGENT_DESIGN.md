# 生成视频质量评测 Agent — 设计说明

> 用大模型看视频、对照提示词，给出可核查的质量结论。
> 目标：把「模型觉得好不好」变成「每条结论都能指到具体画面和时间」。

---

## 1. 一句话概括

给定一个生成视频（Kling / Seedance）+ 它的提示词（I2V 还有参考图），系统输出：

- **一个结论**：通过 / 建议复核 / 拦截
- **五个维度分**和一个加权总分
- **一张三级维度明细表**（每条要么通过、要么不通过并附时间点证据）
- **一份可回看的报告**：每一步调用了什么、输入什么、输出什么

核心原则：**判断交给大模型，但拦截不完全信任大模型**。模型负责「看到什么、是否违反」，程序负责「能确定性检测的就别问模型」和「出现关键问题必须拦住，高画质分不能抵消」。

---

## 2. 整体流程（七步）

```
① 视频文件检查     ── 程序（ffprobe/ffmpeg）
② 抽取关键画面     ── 程序（运动感知采样）
③ 拆解提示词要求   ── 大模型（文本 + 参考图）
④ 看视频、记录画面 ── 大模型（整段视频输入）→ 并指出「看不清、需放大」的时刻
④b 细看重点画面    ── 大模型（原生分辨率大图）→ 确认或推翻上一步的怀疑
⑤ 逐条核对要求     ── 大模型（纯文本推理）
⑥ 汇总评分与结论   ── 程序（扣分 + 加权 + 强制拦截）
⑦ 生成报告        ── 程序
```

**为什么是「先看视频、再看高清图」两阶段？** 视频送进模型时是被压缩采样的——实测整段 9.1MB 视频只占 **300 tokens**，信息被压得很狠，手指结构、文字内容这类细节根本分辨不出来。所以：

1. 先用视频拿**时序理解**（谁在动、什么顺序、跑车从哪边来）——这是单张图给不了的；
2. 让模型**自己指出**哪些时刻「可能有问题但看不清」；
3. 再对这些时刻抽**原生分辨率大图**复核细节。

实测有效性（跑车案例）：模型指出 2 处可疑，高清复核后 **1 处确认**（"右手手指完全融合成肉块状，失去指节结构" —— 视频采样下只能说"疑似异常"）、**1 处推翻**（"该帧相机尚未出现，无法确认" —— 避免了一次误报）。

**为什么这么切？** 如果直接把视频丢给模型说「打个分」，得到的是一个无法追溯、无法复核、容易灌水的数字。拆开之后：

- 能用传统方法确定性检测的（黑帧、卡顿、时长异常），不浪费模型调用，也不会误判；
- 让模型先**只描述看到了什么**（不下结论），再**拿描述对照要求**做判定 —— 两步分开，判定就有了明确依据；
- 最后的分数和拦截由程序按固定规则算，模型给分偏高时会被拉回来。

## 3. 每一步具体怎么做

### ① 视频文件检查（程序）

`ffprobe` 读元信息（分辨率、帧率、时长、编码、帧数），`ffmpeg` 跑两个滤镜做确定性检测：

```
blackdetect=d=0.2:pix_th=0.10   # 持续黑帧
freezedetect=n=0.003:d=0.5      # 冻结/卡顿
```

再校验「帧数 ≈ 时长 × 帧率」，偏差 >15% 判为帧数异常。产出一个 0–100 的检查分和问题清单。

> 这一步不问模型：黑帧、时长异常这类问题用信号处理判得又快又准，交给模型反而不稳。

### ② 抽取关键画面（程序，重点）

**要解决的问题**：均匀抽帧会漏掉高速运动瞬间。网球旋转、跑车驶过这类问题恰好就发生在动作最快的那零点几秒；均匀 1fps 抽帧很可能正好跳过。

**做法**：先算出「每一帧有多少东西在动」，再在动得最厉害的地方加密取帧。全程只用 ffmpeg，不引入 numpy / opencv。

**第一步 · 算逐帧运动量**

```bash
ffmpeg -i in.mp4 -vf "fps=8,scale=160:-1,
                      tblend=all_mode=difference,
                      signalstats,
                      metadata=print:key=lavfi.signalstats.YAVG" -f null -
```

原理拆解：

| 滤镜 | 作用 |
|---|---|
| `fps=8,scale=160:-1` | 降到 8fps、宽 160px —— 只是为了测运动量，不需要高清，快 |
| `tblend=all_mode=difference` | **把每一帧变成「它和前一帧的差」** —— 没动的地方变黑，动了的地方发亮 |
| `signalstats` → `YAVG` | 算这张差值图的**平均亮度** —— 亮度越高＝这一帧动得越多 |
| `metadata=print` | 把每帧的 `pts_time`（时间）和 `YAVG`（运动量）打出来 |

于是得到一条运动量曲线：`[{time: 0.125, motion: 1.07}, {time: 0.25, motion: 0.96}, ...]`

**第二步 · 找出高运动窗口**

对这条曲线算均值 μ 和标准差 σ，取阈值 `μ + 0.8σ`；超过阈值的相邻采样点合并成一个「快动作区间」。

跑车案例实测：识别出 `3.9s–4.9s` 一段，峰值运动量 38.98（远高于其他时段的 ~1）—— 正是跑车驶过 + 相机出现的那一秒。

**第三步 · 排采样计划**

```
基础网格：全片均匀取 N 帧（保证不漏任何时段）
  ＋
加密帧：按运动量排序，取最高的若干帧补进来
  ↓
按最小间隔 0.12s 去重、总数封顶 12 帧（超了优先保留加密帧）
```

**第四步 · 一次 ffmpeg 抽完**

把时间换算成帧号，用 `select` 表达式一趟抽出来（不是每帧起一个进程）：

```bash
ffmpeg -i in.mp4 -vf "select='eq(n\,12)+eq(n\,36)+eq(n\,99)',scale=512:-1" -vsync 0 out_%03d.jpg
```

**产出**：每张帧带 `时间戳` + `是否加密帧` 标记。网球案例实测取 9 帧，其中 4 帧集中在片尾 4.0–4.75s 的高运动窗口。

> 任一步失败（探测不到运动、抽帧报错）都会**自动回退到均匀抽帧**，不会卡住流程。

### ③ 拆解提示词要求（大模型）

把提示词全文（I2V 附参考图，base64）交给模型，要求它输出**可核对的要求清单**，而不是复述：

```json
{"id":"C4","category":"动作","statement":"画面前方必须有一辆跑车驶入或出现",
 "source":"突然前方来了一辆跑车","hardness":"hard","dimension":"dynamic"}
```

同时程序强制注入 4 条基线要求（崩坏、物理合理性、渲染观感、主体时序一致性），防止模型漏掉通用质量项。

跑车案例实测拆出 14 条要求。

### ④ 看视频、记录画面 + 初步判断（大模型）

**把整段视频以 base64 直接交给模型**（Gemini 原生视频理解）：

```json
{"inline_data": {"mime_type": "video/mp4", "data": "<base64>"}}
```

同时附上：全片缩略拼图（快速定位）、参考图、以及第②步算出的高运动区间提示（「请重点核对这些区间」）。

- 视频 >30MB 时自动降级为「关键帧 + 缩略拼图」，避免请求超限（可用 `GEMINI_VIDEO_MAX_MB` 调）。
- **这一步只送视频，不再送缩略拼图**：整段视频已含全部帧，再塞一张低清拼图既冗余、又比视频贵得多（实测拼图 1,080 tokens vs 视频 300）。

这一步产出**三部分**：

1. **可见事实**（`observations`）—— 只描述看到了什么，不下结论，看不清写 `not_observable`；
2. **初步判断**（`preliminary_issues`）—— 对每个评测维度给一个初判 + 证据；
3. **需放大确认的时刻**（`focus_intervals`）—— 模型自己指出「这里可能有问题但视频分辨率下确认不了」。

> **为什么让观察器也判一次？** 它是唯一真正「看过视频」的环节，掌握的信息最全；只让它描述、不让它判，等于浪费了它的判断力。但初判**不是最终结论** —— 第⑤步的验证器会基于事实独立再判一次，两边结论交叉比对：
> - **一致** → 置信度更高；
> - **分歧** → 该维度标记「需人工复核」，在报告和左栏明确列出。
>
> 这样既保留了「事实与判断分离」的可审计性，又用两次独立判断互相佐证。

实测（跑车案例，原生视频）模型输出：

> 「一辆红色跑车在男子**身后**的背景中从左向右行驶穿过画面」
> 「男子抬起左手时，手中**凭空出现**了一台黑色相机，并没有做出从背包里掏出相机的动作」
> 「手部与相机交界处存在模糊和结构不清晰的生成痕迹」（崩坏 L2）

> 用整段视频比抽帧更准：手指粘连、片尾字幕这类时序细节，抽帧容易漏。

### ④b 细看重点画面（大模型，原生分辨率）

按④指出的时刻用 ffmpeg 抽**原生分辨率大图**（`-q:v 2`，不降采样），连同「此前怀疑什么」一起送回模型，只做一件事：**在高清图上确认或推翻这些怀疑**。

**一个关键实测发现：图片 token 与分辨率无关。**

| 输入 | prompt tokens |
|---|---:|
| 整段视频 9.1MB | **430**（video 300 + audio 125） |
| 缩略拼图（每格 200px） | **1,085** |
| 512px 关键帧 | **1,085** |
| **原生 1200×1724 帧** | **1,085** |

512px 和原生 1200px **收费完全一样**。所以此前把关键帧压到 512px 是**一分钱没省、白丢细节**；现在复核一律用原生分辨率。

模型没指出可疑时刻时，退回到运动量最高的区间峰值兜底。视频过大走抽帧降级时跳过本步（已经送过帧了）。

### ⑤ 逐条核对要求（大模型）

输入 = ③的要求清单 + ④的画面描述 + ④的初步判断 + **④b 的高清复核结果** + ①的检查结果（**这一步不再传视频，是纯文本推理**）。

- 初判仅作参考，验证器需基于事实独立判定，不认同就按事实推翻（分歧会被标记）；
- **高清复核与视频观察冲突时，以高清结果为准**（它看得更清楚）。

对每条要求判定：`通过 / 不通过 / 看不清 / 不适用` + 严重度(0–3) + 时间点 + 依据。

同时对**固定三级维度清单**逐条判定（见第 4 节）。

**看不清 ≠ 违反** —— 这是防误报的关键：遮挡、模糊时必须输出「看不清」，不能强判为错。

### ⑥ 汇总评分与结论（程序）

见第 5 节。

### ⑦ 生成报告（程序）

产出自包含 HTML（图片 base64 内嵌，无需服务即可打开），含：结论、维度分表、三级明细、关键画面、要求清单、逐条判定、成本统计、每一步的完整输入输出。

## 4. 评测维度体系（固定三级）

维度定义来自 `quality_assessment.md`，定义原文直接作为判定标准喂给模型（定义越精确，判定越稳）。每个视频都逐条核对全部维度：

| 一级 | 二级 | 三级 | 判定标准（节选） |
|---|---|---|---|
| 画面质量 | 画面基础内容 | 曝光光影或色彩异常 | 过曝/欠曝、光影不合理、色彩失真 |
| | | 油腻感 | 饱和度高、对比度等原因导致画面油腻，含场景油腻、毛发油腻、人像油皮假面；看是否影响美感和人物真实性 |
| | | 文字不可读 | ①prompt 要求生成文字但不可读/不准确；②prompt 未要求却出现不可读文字。例：「匿名」写成「医名」 |
| 动态质量 | 动态基础质量 | 生物类结构异常 | 含静态及动态合理性问题，例：转身头扭 |
| | | 非生物类结构异常 | 叉子变形、物体结构异常、气泡形态不对、楼梯扭曲、船桨等硬性物体不稳定 |
| | | 主体间交互异常 | **穿模**、未接触发生交互；视线与书方向相反、没碰到球球自己弹起、弹吉他姿势不合理 |
| | | 不符合物理规律 | 咬一口东西没变少；不合理的消失/分裂/融合；变化发生时刻延迟或未接触即反应 |
| | | 不符合现实常识 | 长时间不眨眼、室内出现不合理的雪、雨滴溅起水花不合理 |
| | | **明显崩坏** | 主体形态破碎、看不出结构：结构崩了、小人脸异常、嘴部崩坏、手指崩坏 |
| | | **轻微崩坏** | 轻微帧间颜色染色或伪影、轻微结构局部画面崩坏 |
| **音频评测** | 音画同步 | 口型匹配度 | 口型提前/滞后/与台词不匹配；拟人/动物尺度放松；核心看嘴部动作幅度与长闭口节奏点 |
| **音频评测** | 音频质量 | 语义质量 | 语义不明、无法辨别台词、发音错误、结巴重复、语速异常、语音空间异常、台词与场景不匹配 |
| **音频评测** | 音频质量 | 音效、音乐质量 | 音效材质异常、辨识度低、动态不合理；旋律/和声听感不协和、乐器丰富度不足、空间音乐异常、音乐持续性差 |
| 提示词一致性 | 时空关系与动作目标 | 相对位置/朝向/动作-目标/时序 与提示词一致 | 例：跑车应从前方驶来、男子转身对车拍摄 |

> 注意两处易错归属：**穿模属于「主体间交互异常」**（不是结构异常）；**崩坏属于「动态基础质量」**，且拆成明显/轻微两个独立三级项。
>
> 「时空关系与动作目标」不在原文档中，是根据跑车案例的核心问题额外加入的提示词一致性维度。

**关于音频**：这批模型是 I2V**A** / T2V**A**（A = Audio），视频自带 AAC 音轨。我们本来就把整段视频（含音轨）送给模型——实测音频占 **125 tokens**，等于**已经在付费但之前没用上**。现在音频维度由观察器在「看视频」那一步一并听、一并判（后续步骤拿不到音频）：既听台词（内容/发音/语速/口型同步），也听台词以外的**环境音效与背景音乐**。无音轨的视频自动记 `not_applicable`。

**软硬之分**：口型匹配度、语义质量是功能性失败（听不懂台词、音画对不上）→ 硬维度；音效/音乐质量偏听感审美 → 软维度（扣分打 6 折、不因「明显」强制拦截，但严重度 3 仍会拦）。

## 5. 打分与拦截规则（程序，确定性）

### 5.1 维度扣分

每条「不通过」按严重度扣分，累加到它所属维度：

| 严重度 | 扣分 |
|---|---|
| 1 轻微 | −8 |
| 2 明显 | −22 |
| 3 严重 | −40 |

油腻感、曝光色彩这类观感项打 **6 折**（不是硬伤，不该一票压死）。

### 5.2 扣分只拉低、不拉高

```
最终维度分 = min(模型给的分, 100 − 该维度扣分)
```

**这条很关键**：模型有时会一边列出 3 条违反、一边给该维度打 100 分。加了这条之后，扣分能把它拉回来，模型灌水拉不高分。

实测：跑车案例 Kling 的动态质量，模型给 20 → 扣分后 **0**；Seedance 的提示词一致性，模型给 80 → 扣分后 **78**。

### 5.3 加权总分

| 模式 | 完整性 | 动态 | 画面 | **音频** | 提示词 | 一致性 |
|---|---:|---:|---:|---:|---:|---:|
| T2V | 13% | 30% | 17% | **15%** | 17% | 8% |
| I2V | 9% | 25% | 13% | **15%** | 13% | 25% |

音频占 15%（A = Audio 是这批模型的一等产出），其余维度在原比例上等比缩放。

模式自动判定、无需人工选择：**有参考图 → I2V，没有 → T2V**（I2VA 集合有参考图，T2VA 没有）。

### 5.4 强制拦截（高分不能抵消）

出现下列情况直接判「拦截」，**不管总分多高**：

- 任一「不通过」严重度 ≥ 3
- 硬性要求「不通过」且严重度 ≥ 2（结构异常、穿模、物理、时空关系不一致等）
- 崩坏程度 ≥ 2（明显崩坏）
- 文件检查发现严重问题（时长/分辨率/解码异常）
- 模型自己判定为 blocked（**不允许程序降级**）

> 这是踩过坑加的：早期版本模型明明报了 3 条关键失败并自判 blocked，却因为失败类型字符串对不上白名单被降级成「建议复核」。现在改为按严重度 + 语义匹配，并且模型的 blocked 不可被推翻。

## 6. 工程设计要点

| 问题 | 做法 |
|---|---|
| **网关限流(429)** | 429/5xx 自动指数退避重试（6→12→18s），实测能穿过限流 |
| **模型 JSON 偶发畸形** | 多级修复级联：去尾逗号 → 截断括号平衡 → 未闭合字符串补全；仍失败则重试一次 |
| **长连接被掐断** | 分析放后台任务，浏览器**轮询**进度（不用 SSE 长连接），断了自动重试 |
| **重复分析浪费** | 每个 `(案例, 视频源, 引擎, 模式)` 的完整报告落盘缓存，命中直接复用、不再调模型；带版本号，结构变更自动失效 |
| **模型输出脏数据** | 列表元素非对象时过滤，三层防御，不让脏数据打断评分/渲染 |
| **可审计** | 每次调用的 system prompt、输入、原始输出、解析后 JSON 全量落盘，报告里可展开 |

## 7. 成本（分析一个视频）

一次完整分析 = **3 次大模型调用**（跑车案例 Kling 实测，9.1MB 视频）：

| 调用 | 输入模态 | 输入 tokens | 输出 | 思考 | 合计 |
|---|---|---:|---:|---:|---:|
| ③ 拆解提示词要求 | 图片（提示词 + 1 张参考图） | 1,591 | 954 | — | 3,516 |
| ④ 看视频、记录画面 | **视频**×1 + 图片×2 | 4,526 | 823 | — | 7,118 |
| ⑤ 逐条核对要求 | 纯文本 | 3,184 | 2,640 | — | 7,806 |
| **合计** | 视频 1 / 图片 1 / 纯文本 1 | **9,301** | **4,417** | **4,722** | **18,440** |

- **上传媒体 9.7 MB**（视频 base64），**端到端 162 秒**。
- 输入 token 按模态：文本 5,636 / 图片 3,240 / **视频 300** / 音频 125
  —— 视频虽然 9.7MB，但只占 300 tokens：模型对视频做了高度压缩的表征，**传整段视频并不比传 8 张关键帧贵**（图片反而占 3,240）。这是继续用原生视频输入的重要依据。
- Seedance 同案例：3 次调用、合计 19,826 tokens、上传 5.0MB、126 秒。
- **命中缓存时 0 次调用、0 token**。

报告里「本次分析成本」板块会按调用步骤列出上述明细。

> 成本量级参考：单个视频 ≈ **1.8–2 万 tokens、3 次调用、2–3 分钟**。128 个案例跑一遍两个模型 ≈ 768 次调用、约 470 万 tokens。

## 8. 真实案例：跑车空间关系（Kling vs Seedance）

**提示词**：「男人站在广场上，突然**前方**来了一辆跑车…他从背包里掏出相机开始连拍…镜头环绕男人。」

**Kling 的核心问题**（也是这条视频最大的问题）：**时空关系与动作目标不一致** —— 模型原话：

> 「跑车从**身后**驶过，并非从前方驶来，相对位置与 prompt 不一致。」

附带：相机凭空出现（违反物理/常识）、手部结构粘连变形（明显崩坏）。

| 维度 | Kling (A) | Seedance (B) |
|---|---:|---:|
| 动态质量 | 40 | 80 |
| 画面质量 | 90 | 100 |
| 提示词一致性 | **40** | 70 |
| **加权总分** | **76** | **91** |
| **结论** | **拦截** | **拦截** |

**结论与人工判断一致：Seedance 明显优于 Kling**，差在提示词一致性。

**Kling 的核心失败（每次运行都稳定命中）**——模型原话：

> 「跑车出现在老人**身后**而非前方；老人**朝正前方拍摄，未对准跑车**；**镜头未环绕**老人。」

一句话点出三处提示词不一致，其中「未环绕」还是人工复核时漏看的。**Seedance 相比之下**：男子确实侧身转向、相机对准了跑车，只是「从夹克内侧而非背包掏出相机」（S2，较轻）。

**这个维度的判定为什么可靠**：定义里强制模型按顺序推理——先用肩线/躯干/脸/脚尖确定**身体朝向**，再定另一主体相对该朝向的**世界坐标**位置与轨迹，并明确「prompt 里的前方/身后指世界坐标，不是画面左右；镜头环绕时屏幕左右会变、世界坐标不变」。没有这条约束，模型容易只看单帧的屏幕左右位置而判错。

## 9. 已知问题：结构类维度的误报（尚未解决）

**现象**：「生物类结构异常」在这条案例上会误报——模型把**浅景深虚化、运动模糊、源分辨率不足**导致的手指发软，判成「手指完全融合成肉块状、失去指节结构」（S3）。

**验证方式**：把对应时刻抽成原生分辨率大图逐一人工核对——手指是能数出来的，分界虽软但可辨，属正常摄影效果，不是生成缺陷。

**已做的缓解**：

1. 维度定义里写明判定门槛：只有**结构本身错了**（多指少指、解剖走向不可能、形态破碎到认不出）才算；虚化/模糊/遮挡/分辨率不足**一律不算**，看不准记 `not_observable`；
2. 明确告诉模型「不要为了填满清单而找问题，多数维度在多数视频里都是 pass，误报的代价和漏报一样大」；
3. 把**源分辨率**告知模型做校准（720p 的软是分辨率所致，不是缺陷）；
4. 高清复核步骤：若原生分辨率下仍看不清，须报「该分辨率下无法判定」而非确认。

**效果**：误报率明显下降，但**仍不稳定**——多次运行之间会在 A/B 之间跳（这次判 Kling，下次判 Seedance），约一半概率仍会误报 S2。

**根因**：单次 VLM 判断在"软画面"上方差很大，靠 prompt 约束压不干净。

**建议的彻底解法**（未实施）：对结构类维度做**多次采样投票**（同一判断跑 3 次取多数），用成本换稳定性；或引入传统 CV（手部关键点检测）做交叉验证。

> **重要**：这个问题只影响结构类维度。**时空关系与动作目标维度是稳定的**——每次运行都能准确定位跑车方位错误，是可以信赖的。
