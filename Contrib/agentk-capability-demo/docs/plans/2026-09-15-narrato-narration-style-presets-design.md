# Narrato 解说风格预设设计

## 目标

Narrato 此前只有一种解说做法：纪录片式的伴随旁白。使用方反馈"效果不好"，但逐条追查下来，绝大多数具体抱怨并不是文案写得差，而是**做出来的东西不是他们要的品类**。他们要的是影视解说——盖着原片对白复述剧情的那种。这两者不是同一件事做得好坏之分，是两套互相矛盾的创作取向。

本设计引入 `style` 参数，把"一种解说风格需要的全部创作取向"收成一个预设对象，让两个品类在同一条流水线上共存，默认行为保持不变。

## 品类错配：为什么调 prompt 治不好

把纪录片旁白的取向和影视解说的取向摆在一起，冲突是系统性的：

| 取向 | 纪录片伴随解说 | 影视解说 |
|---|---|---|
| 原片对白 | 避让，有信息量的对白不覆盖 | 盖着讲，转述其含义 |
| 剧情 | 严格事件后置，绝不提前说破 | 主动复述，允许提前概括结果 |
| 覆盖率 | 55%–70% | 88%–96% |
| 最长空档 | 5 秒 | 2 秒 |
| 语速 | 2.8–3.5 字/秒 | 4.0–5.0 字/秒 |
| 原声音量 | 0.2 | 0.08 |

关键在于这些取向**不只写在 prompt 里**。"避让对白"同时体现在 `excessive_narration_gaps` 的覆盖判定上：ASR 检测到的对白区间被计为"已覆盖"，因此不要求补解说。这条规则对纪录片是对的，对影视解说则是致命的——影视剧几乎全程有人说话，于是节奏校验会认为整片都已覆盖，模型再怎么被要求"高密度"，校验也不会推着它改。同理，"不剧透"由 `post_event_narration` 开关强制，原声音量是渲染阶段的默认值。

也就是说，一种风格的取向散落在提示词、节奏校验、渲染默认值三处。靠改 prompt 只能改动其中一处，另外两处会把它拉回去。这是"反复调 prompt 但效果上不去"的真正原因。

## 风格预设

`contracts/styles.py` 定义不可变的 `NarrationStyle`，把上述全部取向收进一个对象；调用方只传风格 id。目前有两个预设：`documentary`（默认，行为与改动前完全一致）和 `recap`。

风格通过 `GENERATE_INPUT_SCHEMA` / `CREATE_INPUT_SCHEMA` 的 `style` 字段进入流水线，缺省为 `documentary`，因此所有既有调用方无需改动。工作流在入口解析出 `NarrationStyle`，再贯穿到策划提示词、文案提示词、节奏校验和修订提示词。

两处需要特别说明的联动：

其一，`post_event_narration`（事件后置、不剧透）此前由 patch 开关单独决定，现在改为 `post_event_patch and not style.retell_plot`。复述剧情的风格本就要提前交代情节，这个约束在这里必须让位于风格，否则两条规则会在提示词里互相打架。

其二，`excessive_narration_gaps` 新增 `dialogue_counts_as_coverage` 参数。`recap` 传 `False`，使原片对白不再抑制解说需求，节奏校验因而能真正推动高密度改写。

原声音量只作为前端默认值随风格联动，用户手工调过之后不再被风格覆盖（前端用 `originalVolumeTouched` 标记区分）。

## 顺带修复的两个问题

**上游偶发拒绝会整条挂掉。** `understand_video_segment` 偶尔被上游以 `HTTP 400 / UpstreamRequestRejected` 拒绝（本质是拉取分片失败的暂时性故障，却被包装成不可重试的永久错误）。Narrato 的 `_is_degradable_activity_error` 把它判为不可降级，于是一个窗口失败会杀掉整条流水线。实际上调用方早有完善的降级路径——该窗口退回只用 ASR 证据，并在 `segmentObservation` 里明确告知模型不得推断画面内容。现在上游拒绝走这条降级路径，而 `InvalidArgument`、`Configuration`、`InvalidCoreOutput` 这类真正的契约与配置错误仍然直接失败，不被降级吞掉。

同时把降级规模显式报进进度事件（`3/40 个窗口的视频理解不可用`，附 `visionUnavailableWindows`）。单个窗口偶发降级可以接受，但整片降级意味着视觉模型根本没生效、脚本会退化成纯 ASR 复述，这种情况必须让人看见，而不是悄悄产出一份质量可疑的成片。

**模型会自己填 `pacingWarning`。** `DOCUMENTARY_SCRIPT_SCHEMA` 被当成两个角色用：既是交给模型做约束解码的 `outputSchema`，又是工作流对外发布的产出契约。模型在 schema 里看得见 `pacingWarning`，就往里写"覆盖率约 97%、无连续空档超过 2 秒"这类自我评价——既不可信，又会诱导它为了凑出好看的数字而扭曲文案。

修法是拆分角色而非删除字段：新增 `SCRIPT_GENERATION_SCHEMA`，即产出契约去掉 `pacingWarning` 后的版本，只用于模型侧；对外契约原样保留该字段，由工作流用 `_cadence_warning` 确定性填写。因 schema 带 `additionalProperties: False`，模型现在无法写入该字段。

这个洞此前之所以能一路漏到最终产物，是因为工作流只在**检测到真实节奏问题时**才覆盖该字段；没有真实问题时，模型写的自评就原样留到了输出。

## 验证

单测覆盖风格解析与未知 id 拒绝、`style` 在两个输入 schema 中的接受、原声音量默认值的风格联动与手工覆盖、对白覆盖判定仅对 `documentary` 生效、recap 提示词对剧透与对白策略的反转、以及两份脚本 schema 除 `pacingWarning` 外完全一致。容错方面分别验证首次调用与切片后调用被上游拒绝时降级为 `None`，以及三类契约/配置错误仍然抛出。

实跑验证：一条 120 秒素材以 `recap` 风格走完 `documentary_video`，过程中 `understand_video_segment` 真实发生两次上游拒绝，流水线未中断并正常出片；产出覆盖率 97.3%，开场为钩子句，文案为口语化剧情复述。

## 后续

视频理解 400 的根治不在本仓：分片已经在本地生成，应直接以 `inlineData` 内联发送而非让上游远程拉取，从根本上消除 CDN 竞态。当前的降级只是止血——上游拒绝一旦变频繁，效果会在无人察觉的情况下滑落。

其余已知问题：原声闪避释放过长（`compose_video`，AgentK 主仓）；字幕与原片烧录字重叠，需要避让策略；web 层把参数校验失败吞成 `502 ConnectError`，会把人误导到连接问题上排查。
