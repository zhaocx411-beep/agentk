# 第 5 章 多智能体详细设计文档生成系统中的应用

前两章分别从文档离线索引侧提出了“结构与关键信息感知的自适应语义切片算法（SEAC，第 3 章）”，从在线查询侧提出了“面向智能体角色的动态检索粒度选择方法（MAS-DRG，第 4 章）”，并在 10 个真实工业软件工程项目的冻结基准上完成了严格的定量评估。为进一步验证上述两项核心算法在真实软件工程自动化场景中的工程可用性与集成价值，本章将其置于本课题所依托的**《企业软件项目详细设计文档自动生成系统》**中开展系统设计与离线案例验证。

本章遵循“**系统需求与三层架构剖析 $\to$ 核心运行时框架与子会话隔离机制 $\to$ 详细设计智能体层级编排 $\to$ 可追溯动态检索知识服务（`rag_query`）设计 $\to$ 真实工业会话请求离线案例对比与产出展示**”的脉络展开。需要明确说明的是：为严格遵守企业工程项目代码的冻结管理规范，本章保持原多智能体系统主干业务代码不变，以“标准化检索工具接口设计 + 基于正式实验冻结索引库的真实请求离线案例对比分析”方式，定性与定量相结合地展示 SEAC 与角色动态路由在消除表头丢失、跨接口消歧及源单元可追溯审计方面的关键作用。

## 5.1 系统需求与总体架构

### 5.1.1 应用场景：企业软件项目详细设计文档的自动生成

在大型工业软件（如钢铁冶金生产管控、智慧能源综合监控、企业综合服务一体化平台及船舶数字化建造计划管理系统）的研发交付周期中，《详细设计规格书（Detailed Design Specification）》是承接前期《需求调研会议纪要》《技术协议》《需求规格说明书（SRS）》并直接指导后端微服务编码、前端界面开发与物理数据库建表的核心工程蓝图。一份标准的工业级详细设计文档通常包含以下高度结构化的核心章节：
1. **总体概述与系统架构设计**：涵盖项目建设背景、业务目标、总体应用架构、技术选型（如容器编排 Kubernetes、微服务网关、负载均衡组件）、网络拓扑及非功能性性能验收指标；
2. **业务模块功能详细设计**：针对数十个业务子模块（如设备点检、危险作业审批、能源介质监视、危固废全流程管理等），逐一规定画面布局、功能操作区按钮行为、业务流转状态机与异常处理逻辑；
3. **对外与内部通讯接口详细设计**：以规范化二维表格形式定义上百个跨系统接口（如与 ERP、MES、OA、IoT 平台或政府监管平台对接接口）的接口代码、请求方式（`POST/GET`）、请求路径、调用方向以及出入参字段的名称、类型、长度、格式与必填要求；
4. **物理数据库表结构设计（数据字典）**：定义数十至上百张数据库业务表的表名、所属表空间、中文功能描述，以及表内每个字段的英文列名、数据类型、主键/外键约束、是否允许为空及枚举值字典。

在传统软件工程研发模式下，系统架构师与模块开发工程师需人工翻阅数十份跨阶段前期文档（总字数往往达数十万字、包含数百张复杂表格），手动摘录、对齐并编写详细设计规格书，不仅耗时长达数周，且极易因前期会议纪要变更未能同步至详细设计而引发需求遗漏或接口字段不一致。为此，本课题依托的工程项目构建了基于大语言模型的多智能体详细设计文档自动生成系统。

### 5.1.2 三层总体工程架构

如图 5-1 所示（矢量文件见 [fig5_1_system_architecture.svg](file:///Users/apple/Desktop/毕业设计/小论文/毕业论文/figures/fig5_1_system_architecture.svg)），该系统在软件工程实现上采用高内聚、低耦合的**三层解耦架构**，自顶向下依次由**领域应用编排层（`Multi-Agent-DetailedDesign`）**、**多智能体核心运行时框架层（`Multi-Agent-Framework`）**以及**底层编译工具链与知识存储层（`binary-tools` & Vector Store）**组成：

1. **第一层：领域应用编排层（`Multi-Agent-DetailedDesign`）**
   面向具体的企业软件详细设计生成业务，以声明式配置文件（`config/agents/**/*.yaml` 与全局 `config.yaml`）定义了层级化的专业智能体角色群（包括顶层协调智能体 `detailed_design_agent`、章节概述智能体 `overview_agent`、模块与接口设计智能体 `module_agent` / `interface_agent` 以及数据库与规格约束核查智能体 `database_agent` / `constraint_agent`）、各章节撰写提示词模板、领域技能包（Skills）以及文档分章产出规范。应用层不包含硬编码的底层通信或检索逻辑，所有智能体行为均通过配置驱动挂载至下层框架。
2. **第二层：多智能体核心运行时框架层（`Multi-Agent-Framework`）**
   基于 Python 构建的通用多智能体运行时底座（核心源码位于 `src/multi_agent_framework/core/` 与 `built_in/`）。该层提供全局单例管理器（`Manager`），统一负责配置解析、大语言模型多后端适配、智能体（`Agent`）与会话（`Session`）生命周期管理、基于 `session_create` / `session_query` 的父子会话层级调度、文件读写工具集以及**内置检索增强生成模块（`built_in/rag/chroma_retriever.py`）**。本论文第 3 章提出的 SEAC 自适应切片器与第 4 章提出的 MAS-DRG 角色感知动态粒度路由器即无缝嵌入在该层的内置 RAG 服务中。
3. **第三层：底层编译工具链与工程知识存储层（`binary-tools` & Vector Store）**
   提供高性能的外部存储与确定性工业文档编译能力。一方面，利用嵌入式向量数据库 **Chroma** 持久化存储经 SEAC 切片并由 `BAAI/bge-m3` 编码的父块与表格行子块向量及全链路出处元数据（`Unit ID`）；另一方面，集成基于 Rust 与跨平台二进制封装的编译工具链（`binary-tools`），包括用于将智能体生成的结构化文本编译为工业标准 PDF 文档的 **Typst 排版引擎**，以及用于将架构描述代码渲染为高清矢量架构图与时序图的 **PlantUML / Mermaid 渲染器**。

## 5.2 多智能体框架设计

`Multi-Agent-Framework` 的核心设计目标是在保障多智能体并发协作灵活性的同时，严格控制单个智能体的上下文窗口负载（呼应第 2.3.2 节中 Hua & Xiao[49] 与 NativeScope[50] 揭示的子会话上下文管理准则）。其核心架构由以下四项机制支撑：

### 5.2.1 `Manager` 单例与声明式配置驱动（TOML / YAML）

框架采用全局单例模式（Singleton Pattern）设计核心控制器 `Manager`。在系统启动阶段，`Manager` 自动扫描并解析项目根目录下的 `config.yaml`（或 `TOML` 配置文件）及 `config/agents/` 子目录树，完成三项初始化工作：
* **模型池注册**：读取大语言模型服务端点、API 密钥、温度参数（`temperature`）与最大输出 Token 限制，支持为不同复杂度的智能体绑定差异化的基座模型；
* **工具与技能装配**：通过反射机制将 `built_in/tool/` 下的系统工具（如文件操作、会话管理、命令执行、知识检索 `rag_query`）注册至全局工具注册表，并根据各智能体 YAML 配置中的 `tools` 与 `skills` 字段实行按角色最小权限挂载；
* **智能体蓝图实例化**：将每个角色的提示词模板（`system_prompt`）、允许调用的子智能体白名单及输出约束封装为不可变的 `Agent` 蓝图对象。这种**代码与业务配置彻底分离**的设计，使得新增或调整详细设计章节角色无需改动任何框架核心代码。

### 5.2.2 `Agent`、`Session` 与 `Tool` 核心抽象

框架在面向对象设计上将“静态角色定义”与“动态运行时状态”严格解耦为三个核心抽象类：
1. **`Agent`（智能体静态蓝图）**：封装角色的静态属性，包括唯一角色标识符（`role_name`，如 `interface_agent`）、系统提示词模板、绑定的模型配置以及可用工具名称集合。`Agent` 本身不保存任何对话历史，因此同一 `Agent` 蓝图可被并发实例化为多个独立的运行时会话。
2. **`Session`（会话运行时容器）**：代表某一个 `Agent` 为执行特定子任务而创建的独立运行实例（分配唯一 `session_id`）。每个 `Session` 内部维护私有的消息历史列表 $\mathcal{H}_{\text{mem}}$（包含 `system`、`user`、`assistant` 及 `tool` 角色消息）、当前工作目录上下文以及遵循 ReAct 范式[43]的“推理—工具调用—观测”主循环状态机。
3. **`Tool`（标准化工具接口）**：所有外部能力均继承自统一的 `Tool` 基类，包含工具名称（`name`）、供大模型理解参数规范的 JSON Schema 描述（`description` 与 `parameters`）以及异步/同步执行入口函数 `execute(**kwargs)`。

### 5.2.3 子会话机制：`session_create` 与 `session_query` 实现层级调度

为解决单智能体在编写数百页详细设计文档时因上下文累积导致的“中间信息迷失”[11]与注意力分散[56]，框架在 `built_in/tool/session_manage.py` 中设计了原生支持树状递归调度的**父子会话管理机制**：

* **`session_create(agent_name, task_context)`**：允许当前父会话根据任务拆解需要，指定目标下属智能体名称 `agent_name` 动态创建一个全新的子会话实例 $S_{\text{sub}}$，并返回唯一的 `sub_session_id`。子会话仅接收父会话显式传入的精简任务上下文 `task_context`，而不继承父会话庞杂的历史消息流；
* **`session_query(sub_session_id, instruction)`**：父会话通过该工具向指定子会话发送具体的分章或分模块撰写指令 `instruction`。子会话 $S_{\text{sub}}$ 在其完全隔离的私有上下文窗口 $\mathcal{H}_{\text{sub}}$ 中独立执行多轮 `rag_query` 知识检索、表格解析与 `.typ` 章节源码写入；待子任务执行完毕后，`session_query` 仅将子会话生成的最终结论摘要或产出文件相对路径返回给父会话。

通过这一机制，底层执行智能体在核对数十张数据库表或上百个接口参数时产生的数万 Token 中间检索观测值被完全封闭在子会话 $S_{\text{sub}}$ 内部，待该模块写完落盘后即可随子会话生命周期结束而释放，从而保证顶层协调智能体的主会话窗口 $S_{\text{root}}$ 始终保持洁净高效。

### 5.2.4 技能（Skill）系统

针对详细设计文档中高度专业化的排版与制图规范（如 Typst 复杂跨页表格语法、PlantUML 组件图/时序图语法规范、数据库三范式设计规范），若将所有规范说明全部硬塞入每个智能体的常驻 `system_prompt`，会造成严重的常驻 Token 浪费。为此，框架设计了按需注入的**技能（Skill）系统**：将各类专有规范封装为独立的 Markdown 技能包文件；当智能体进入特定子任务（如生成接口时序图或编写 Typst 表格）时，运行时引擎动态加载对应 Skill 指令块注入当前会话，实现领域技能知识的模块化复用。

## 5.3 详细设计智能体编排与生成工作流

### 5.3.1 智能体层级与分工

在 `Multi-Agent-DetailedDesign` 应用层中，系统仿照大型工业软件工程团队的组织架构，构建了如图 5-2 左侧所示的四级协同拓扑（矢量文件见 [fig5_2_agent_orchestration.svg](file:///Users/apple/Desktop/毕业设计/小论文/毕业论文/figures/fig5_2_agent_orchestration.svg)）：

1. **顶层协调层（`detailed_design_agent`）**：作为整个文档生成任务的根节点（`S_root`），负责解析用户输入的工程项目目录、初始化输出工作区、规划《详细设计规格书》的章节大纲树，并按章节依赖顺序创建和调度下层章节级与模块级子会话；同时负责跨模块核心业务流转（Process）的全局统筹。
2. **章节概述层（`overview_agent`）**：受顶层智能体委托，负责撰写第 1 章（引言与项目背景）、第 2 章（总体架构设计、技术架构、硬件与网络部署架构）及各业务板块的功能架构综述（Feature Overview）。
3. **模块与接口设计层（`module_agent` / `interface_agent`）**：负责具体业务子模块的画面原型说明、逻辑处理规则以及对外/内部通讯接口章节的撰写。其中接口设计要求精确对齐每个 API 的请求方式、路径、发起/接收系统及出入参字段规约表。
4. **底层数据库与规格核查层（`database_agent` / `constraint_agent` / `requirement_trace_agent`）**：深入每个业务模块内部，负责生成物理数据库表结构字典（表名、表描述、字段名、类型、长度、必填约束）、核查非功能性数值指标（如并发响应时间、仪表管径与流量范围、培训工期）以及核对前期需求调研会议纪要中的决议条款。

### 5.3.2 文档生成四阶段工作流与 Typst 编译工具链

一次完整的企业软件项目详细设计文档自动生成过程包含四个标准阶段（见图 5-2 左下部分）：
1. **阶段一：工作区初始化与前期语料入库**：系统扫描输入工程项目的原始资产目录（含《技术协议》《需求规格说明书》《需求调研会议纪要》及已有的接口/数据库草案），建立标准化的章节输出目录结构，并触发 SEAC 切片器完成项目文档库的层次化切片与 Chroma 向量索引构建；
2. **阶段二：全局架构解析与分章任务派发**：顶层 `detailed_design_agent` 通过宏观检索把握项目整体业务边界与子系统划分，生成全局架构摘要与章节任务清单，依次通过 `session_create` 与 `session_query` 唤醒 `overview_agent`、`interface_agent`、`database_agent` 等专职子会话；
3. **阶段三：子会话按角色精准检索与分章 `.typ` 撰写**：各专职子智能体根据自身分配的章节任务，调用 `rag_query` 工具从前期工程文档库中检索支撑证据，编写符合工业标准的 Typst 章节源码文件（`.typ`）及内嵌的 PlantUML / Mermaid 架构与时序图代码；
4. **阶段四：图表渲染、Typst 联合编译与溯源校验**：底层 `binary-tools` 工具链首先将各章节生成的 PlantUML / Mermaid 源码编译为矢量图形，随后调用 Typst 编译器将主控文件 `main.typ` 与各分章 `.typ` 文件联合编译为排版精美的《详细设计规格书.pdf》最终交付件（如系统实际产出的 100 余页《船舶数字化建造计划管理系统详细设计文档.pdf》）。

## 5.4 可追溯动态检索知识服务的设计

### 5.4.1 系统原有信息获取方式的局限性

在未引入本论文提出的 SEAC 与 MAS-DRG 算法之前，多智能体详细设计系统获取前期项目文档信息主要依赖两种传统方式：一是**“全文直接读取 + 逐层摘要传递”**，即在初始化阶段调用文档读取工具将《需求规格书》或《技术协议》全文分段读入大模型生成摘要文件，再将摘要传递给后续模块智能体；二是**“基于固定大小窗口切片的通用 Chroma 检索”**（即默认 `built_in/rag/chroma_retriever.py` 的固定字符切分模式）。

在真实工业项目运行与 1,209 个历史会话日志的复盘中，上述传统方式暴露出三项严重工程缺陷：
1. **有损摘要压缩诱发细节规则丢失与级联幻觉**：正如第 1.2 节引用的 HaluMem[48] 与 RAPTOR[7] 研究所证实的，前期文档中的数据库字段类型（如 `tinyint` vs `varchar(40)`）、接口日期格式（`yyyy-MM-dd HH:mm:ss`）以及硬件仪表参数（如管径 `DN200`、材质 `304不锈钢`）属于不可压缩的刚性契约细节。经过上层智能体“全文读取 $\to$ 文本摘要”的有损压缩后，超过 $70\%$ 的表格行细节在摘要中被省略，导致下层 `database_agent` 与 `interface_agent` 在编写具体表结构时被迫依靠大模型先验猜测字段名，产生严重的工程幻觉。
2. **固定窗口切片割裂跨页表格导致检索失灵**：当子智能体尝试使用传统固定窗口（`Fixed-512`）检索前期接口文档或数据库字典 XLSX 时，由于表头仅出现在表格第 1 行，后续数十个切片全部沦为丧失列语义的孤立数值串（在第 3 章正式评测中，固定窗口的片段级 Span MRR 仅为 $0.1350$），导致智能体频繁检索失败或将不同接口的参数张冠李戴。
3. **缺乏源文档单元级出处谱系（Provenance Lineage）**：传统全文摘要或固定字符偏移切片无法告诉下游智能体或人类审计工程师“当前生成的接口参数或性能指标究竟源自哪一份技术协议的哪一节、哪一张表的第几行”，导致生成的详细设计文档无法开展自动化合规审计（PEP-AI）[58]。

### 5.4.2 基于 SEAC 与角色动态路由的 `rag_query` 检索服务设计

为彻底解决上述痛点，本研究在不侵入多智能体调度核心代码的前提下，围绕框架内置的 `built_in/rag/chroma_retriever.py` 设计了**基于 SEAC 单一层次化索引与 MAS-DRG 角色动态路由的可追溯知识检索服务（`rag_query`）**。其完整工作流如图 5-2 右侧所示：

1. **离线索引构建层（SEAC 引擎驱动）**：
   在项目初始化阶段，调用 `seac_chunking` 解析项目文档集 $\mathcal{D}$，提取携带唯一稳定标识 `unit_id`（格式为 `文档名:B区块号` 或 `文档名:B区块号#R行号`）的结构化单元序列；通过 SEAC 四信号透明边界打分（式 3-11）与文档自适应阈值 $\theta_D$（式 3-12）切分生成章节受保护的父块集合 $P$，并为每条表格行按表头显式绑定公式（式 3-2）生成独立子块集合 $C$。使用 `BAAI/bge-m3` 统一编码 $P \cup C$ 后存入单个 Chroma 集合（Collection），每个向量条目完整挂载 `chunk_type`（`parent` 或 `child`）、`parent_chunk_id`、`section_path` 与 `source_unit_ids` 元数据。
2. **在线角色路由层（MAS-DRG 引擎驱动）**：
   当任意智能体会话 $S$ 调用 `rag_query` 工具时，工具执行器直接从当前 `Session` 上下文中读取发起调用的智能体角色标识 `agent_role`（或由调用参数显式传入），通过第 4 章标定的**角色—粒度路由表（表 4-2）**在 $O(1)$ 时间内映射得到该角色专属的检索配置二元组 $(\alpha_r, m_r)$：
   - 若 `agent_role` $\in \{\text{database\_agent}, \text{constraint\_agent}, \text{requirement\_trace\_agent}\}$（执行层精确事实型 $T_{\text{atomic}}$）：自动路由至 **$\alpha_r = 0.0,\; m_r = \text{Child-Only}$**，完全屏蔽父块背景噪声，直接返回带表头与章节前缀的精炼子块（平均仅 $\sim 48.3\text{ tokens}$）；
   - 若 `agent_role` $\in \{\text{interface\_agent}, \text{module\_agent}\}$（模块层层次上下文型 $T_{\text{hier}}$）：自动路由至 **$\alpha_r = 0.35,\; m_r = \text{Hybrid}$**，联合父块接口章节得分与子块参数行得分完成跨接口消歧，并返回“父块上下文 + 高亮触发参数行”；
   - 若 `agent_role` $\in \{\text{overview\_agent}, \text{detailed\_design\_agent}\}$（协调与章节层概述型 $T_{\text{macro}}$）：自动路由至 **$m_r = \text{Parent-Only}$**（精度优先策略下 $\alpha_r = 0.0$，三档策略下流程类 $\alpha_r = 1.0$），向智能体返回语义连贯、结构完整的章节父块（平均 $\sim 212.2\text{ tokens}$）。

### 5.5.2 分层定性剖析：证据完整性、消歧能力与可追溯性

以下结合表 5-1 中的具体返回文本内容，深入剖析三种方案对下游智能体文档生成质量的实质影响：

#### （1）执行层案例剖析（案例 1 `P08/QS008` 与案例 2 `P04/QA016`）：消除表头剥离与父块均值稀释

在烟台华新不锈钢能源管理项目（`P08`）中，规格约束核查智能体（`constraint_agent`）在核对能源计量仪表选型表时发出请求 `QS008`：“*新增能源计量仪表清单中，‘氧气总产出’表的管径、管道材质和流量范围要求分别是什么？*”。真实证据位于《模块7-能源管理-技术协议-1207.docx》第 `B0222` 号硬件清单大表的第 21 行（`模块7-能源管理-技术协议-1207:B0222#R021`）。
* **固定窗口（`Fixed-512`）的失效机理**：由于该硬件清单表长达数十行，固定窗口在第 5 行附近便耗尽了 $512\text{ tokens}$ 配额。当切到包含第 21 行“氧气总产出”的块时，表头（`序号 | 检测点名称 | 品牌 | 性能参数及要求`）早已被留在前序块中；同时该块混入了前后十余行其他介质（氮气、氩气、蒸汽、压缩空气）的涡街流量计参数，导致向量相似度被严重拉低，**单元级排名跌至第 17 名（完全滑出 Top-5 窗口）**，且因跨块硬切导致 `span_rank = None`。
* **SEAC 静态配置（$\alpha = 0.35$）的次优瓶颈**：SEAC 虽然通过表头绑定生成了精确匹配第 21 行的子块，但由于静态配置强行叠加了权重为 $\alpha = 0.35$ 的整表父块得分 $S_p(P_k, q)$，而涵盖多行不同介质仪表的父块整体向量与“氧气总产出”单点查询的余弦相似度较低，反而将该父块的总排名拖累至**第 6 名**（刚好错失 Top-5 召回阈值）。
* **本文角色动态路由（MAS-DRG）的优势**：路由器识别到调用者为执行层 `constraint_agent`，自动将融合权重切换为 **$\alpha = 0.0$** 并启用 **`Child-Only` 返回模式**。此时排名完全由表头绑定的第 21 行子块独立决定，**直接跃升至第 1 名（Rank = 1）**！返回给智能体的文本块仅含 $59.3\text{ tokens}$：
  > `[Section] 硬件清单`
  > `氧气总产出 | 川仪 | 1.名称：涡街流量计 2.测量介质:氧气 3.规格：管径：DN200；管道材质：304不锈钢；压力范围：0-25kpa；流量范围：（0-14000）m3/h；计量精度：2.0级以上... [Unit: 模块7-能源管理-技术协议-1207:B0222#R021]`

  同样地，在天津钢管设备管理系统（`P04/QA016`，查询 `MA_EQ` 表用途）与晋钢综合服务平台（`P06/QA020`，查询 `ISM_PERSON_INFO` 表用途）中，`database_agent` 在静态融合 $\alpha=0.35$ 下分别排在第 3 名和第 5 名（受同表数十行字段定义稀释），而经角色动态路由切换至 $\alpha=0.0,\; \text{Child-Only}$ 后，**两道题双双以第 1 名（Rank = 1）精准命中表描述首行**，且单块 Token 消耗从固定窗口的 $507\text{ tokens}$ 锐减至 **$38.7 \sim 47.8\text{ tokens}$**，既杜绝了同表无关字段的上下文污染，又提供了精确到 `#R001` 的行级出处。

#### （2）模块层案例剖析（案例 4 `P05/QA011`）：父子联合打分消除跨接口同名参数歧义

在津西钢铁设备管理系统项目（`P05`）中，接口设计智能体（`interface_agent`）在编写“机旁库储位信息查询接口”出入参规约表时发出查询 `QA011`：“*机旁库储位信息查询接口的请求参数 `size` 的参数类型和是否必填是什么？*”（黄金证据单元：`津西钢铁设备管理系统项目-详细设计规格-接口文档:B0019#R003`）。
* **纯子块检索（$\alpha = 0.0$）的同名冲突困境**：在大型接口规格书中，几乎所有分页查询接口（如备件出入库查询、维修工单查询、储位信息查询）的参数表都包含名为 `size`（每页数据大小）和 `current`（当前页码）的参数行，且各表行文本高度相似（均为 `size | Long / Integer | 是 | 每页条数`）。若仅依赖子块打分（$\alpha = 0.0$），检索器极易被其他接口章节下的 `size` 参数行干扰，导致正确接口下的子块跌至第 2 名（在 `P07/QA004` 查询“获取人员信息接口返回参数 `name`”时同样因多表同名参数跌至第 2 名）。
* **本文角色动态路由（MAS-DRG）的优势**：路由器识别到调用者为模块层 `interface_agent`，自动路由至 **$\alpha = 0.35,\; m_r = \text{Hybrid}$（父子混合返回）**。一方面，$\alpha = 0.35$ 的父块得分项 $S_p(P_k, q)$ 充分利用父块中包含的章节标题与接口说明正文（`2.1.2.1 机旁库储位信息查询接口`），精准锁定目标接口所在的父块 `P0012`，助推正确结果在 `P05/QA011` 与 `P07/QA004` 上**双双稳居第 1 名（Rank = 1）**；另一方面，`Hybrid` 返回模式将父块中的接口整体定义与触发命中的 `#R003` 参数行（`size | Long | 是 | 每页数据大小`）一并返回给 `interface_agent`，确保生成的接口文档既不张冠李戴，又具备完整的接口上下文。

#### （3）协调与章节层案例剖析（案例 5 `P09/QA014`）：保护宏观业务流程论述的连贯性

在烟台华新环保管理项目（`P09`）中，顶层 `detailed_design_agent` 在统筹编写业务协同流程与建设成效综述时发出查询 `QA014`：“*系统通过什么方式提高环保业务的办公效率与协同能力？*”（黄金证据位于《模块8-环保管理-技术协议-1218.docx》第 `B0113` 单元）。
* **固定窗口与碎片化返回的缺陷**：固定窗口因将相邻章节与列表项混杂拼凑，排名跌至第 12 名；而若像执行层那样仅返回单句或单行子块，协调层智能体将丢失前后句关于“线上化、无纸化业务办理模式”与“减少人工操作与冗余流程”的完整因果论述链条。
* **本文角色动态路由（MAS-DRG）的优势**：路由器为 `detailed_design_agent` 自动匹配 **`Parent-Only` 完整父块返回模式**（在三档策略下以 $\alpha = 1.0$ 直接排至**第 1 名**，两档策略下亦稳定在 Top-4 内），向智能体返回包含完整小节标题路径（`项目目标与效果 > 项目效果`）与连贯论述段落的父块 `C0097`（约 $246.6\text{ tokens}$，较固定窗口节省 $51.7\%$ 的冗余上下文），直接支撑高质量章节综述的生成。
