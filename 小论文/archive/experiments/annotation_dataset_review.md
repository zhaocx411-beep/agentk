# 现有标注集质量审计

审计对象：

- `workbench/P01|P02|P03/qa_review_set.json`
- `workbench/P01|P02|P03/candidate_breakpoints.json`
- 对应 `corpus.json`

本报告只审计现状，不修改任何标注。

## 总体结论

现有标注集适合作为自动生成的预标注池和算法调试集，但暂时不适合作为论文最终金标准。

优点：

- 三个项目均有 36 条 QA，共 108 条。
- QA 的证据块全部存在，来源文档和章节均能对应。
- 108 条 `gold_evidence_span` 均能在对应证据块中找到。
- 问题覆盖 API、数据库、约束、功能、流程、数值等多种文档内容。

主要风险：

1. 边界标签完全由构造规则预先决定，当前没有人工标签。
2. QA 中超过一半是泛化模板问题，问题自然度和事实指向性不足。
3. 检索评价只使用块级 `gold_evidence_id`，完全没有使用已标注的 `gold_evidence_span`。
4. 表格问题只需命中同一张表的任意一行即可得分，明显放宽了命中条件。
5. 数据量较小、重复事实较多，单条样本即可明显改变指标。
6. P01 存在两套不同的标注生成路径，数据版本来源未锁定。

## 数据概况

| 项目 | QA 数 | 边界候选数 | 人工 QA 复核数 | 人工边界标签数 |
|---|---:|---:|---:|---:|
| P01 | 36 | 68 | 0 | 0 |
| P02 | 36 | 43 | 0 | 0 |
| P03 | 36 | 68 | 0 | 0 |
| 合计 | 108 | 179 | 0 | 0 |

每个项目只有 36 条 QA，因此一条问题会使 Hit@K 改变约 2.78 个百分点。

## QA 标注审计

### 机械一致性

- 108/108 个 `gold_evidence_id` 均存在。
- 108/108 个 `gold_evidence_span` 均能在对应块中找到。
- 来源文档与章节路径未发现机械错配。
- API 参数答案是由表格字段组合生成，并非原文连续文本；这种情况本身合理，但应由人工确认字段解释是否正确。

### 模板化与自然度

55/108 条 QA 属于以下泛化模板：

- “某章节中规定了什么约束？”
- “某章节支持或提供什么能力？”
- “某章节描述了什么实现或处理过程？”
- “某章节中描述了什么数量、时长或比例要求？”

这些问题经常使用“功能描述”“项目背景”“画面设计”“Research Report”等泛化标题，真实用户很少这样提问，而且标题词会直接匹配检索上下文中的标题元数据。

建议将这 55 条全部列为“必须人工改写”，改成直接、具体、答案唯一的问题。

### 明确错误或强冲突

- `P02/QA002`：问题询问“0717需求调研会议的时间”，答案与正文证据均为 `2025.7.8`。文件名和正文日期冲突，必须回查原始文档并裁决；当前样本不能作为金标准。
- `P03/QA003`：原文是“请求方式：HTTP POST”，自动抽取答案只保留了 `HTTP`。如果问题问“请求方式”，更合理的答案应至少包含 `POST`，当前答案不完整。

### 问题与答案语义不匹配的高风险样本

以下样本的证据存在，但自动生成的问题类型与答案内容不够匹配，建议优先改写：

- P01：`QA023`、`QA028`、`QA034`
- P02：`QA026`、`QA028`、`QA033`、`QA034`
- P03：`QA020`、`QA026`、`QA035`

典型例子：

- `P02/QA028` 问“Research Report支持或提供什么能力”，答案实际描述的是供应方项目经验。
- `P03/QA035` 问硬件实施范围“支持或提供什么能力”，答案实际是网络、电源具备接入条件。
- `P01/QA028` 问“实现或处理过程”，答案实际描述项目建设必要性和政策要求。

### 重复与独立性

27 条 QA 与其他 QA 共享完全相同的证据文本；按每个重复组只保留一条计算，至少有 15 条额外重复样本。

优先去重组：

- P01：`QA017/QA019`
- P01：`QA021/QA025`
- P01：`QA027/QA031`
- P01：`QA029/QA034/QA035`
- P03：`QA018/QA019`
- P03：`QA024/QA032`
- P03：`QA033/QA034`

会议时间和地点共享同一证据块、不同接口均使用 POST 等情况可以保留，但统计时应意识到这些样本并非完全独立。

### 表格证据粒度与评价放宽

40/108 条 QA 的证据来自表格。当前评价只检查块级 `gold_evidence_id`，因此命中同一表格中的错误行也会被记为正确。

| 项目 | 表格 QA 数 | 每条表格 QA 平均可被误判为正确的非证据行数 |
|---|---:|---:|
| P01 | 11 | 12.45 |
| P02 | 16 | 10.56 |
| P03 | 13 | 9.46 |

例如数据库表问题只要检索到该表任意字段行，就会被视为命中表描述证据。`gold_evidence_span` 当前未参与评价。

建议为表格 QA 增加 `gold_evidence_unit_id`，格式类似 `block_id#Rxxx`，并按行级证据评价。

### 难度和泄漏风险

- API 请求方式、数据库表名问题较容易，且问题直接包含接口名、参数名或表名。
- 所有问题均由同一语料规则生成，存在明显词面重合。
- P02 有 4 条请求路径问题，P03 有 1 条请求路径问题，包含内部或业务接口地址。
- 边界候选中还存在人员姓名、会议地点、电话号码等信息。

正式论文公开数据前必须完成脱敏和授权确认。

## 边界标注审计

### 标签由规则直接决定

当前 179 个候选的建议标签与候选类型一一对应：

| 候选类型 | 数量 | 建议标签 |
|---|---:|---|
| `heading_transition` | 65 | 全部 BREAK |
| `same_section_continuity` | 62 | 全部 NO_BREAK |
| `inside_table` | 52 | 全部 NO_BREAK |

这会产生循环评价：结构感知方法本来就按标题切分、保护表格，随后又用同一规则生成的标签评价它。

而且在没有人工标签时，评价代码会直接回退使用 `suggested_label`。因此当前 Boundary F1 不能视作人工真值上的表现。

### 覆盖不足与采样偏差

- 三个项目共有约 2.65 万个基础单元，但只选择了 179 个候选边界。
- 每份文档最多固定抽取约 5 个标题边界、4 个同章节边界和 3 个表格边界。
- 长文档和短文档获得近似数量的候选，样本不能代表真实边界分布。
- 候选主要来自容易按规则判断的位置，缺少同章节主题突变、跨表格语义连续、列表项边界和噪声边界等困难案例。

### 表格边界定义不清

所有表格内部边界均预标为 NO_BREAK，但当前系统会给每个表格行重复附加表头，并且 v6 本身以表格行为检索子块。因此“切分表格行一定破坏表头关系”的预标理由与实际数据表示并不一致。

需要先明确评价目标：

- 如果评价父块上下文完整性，同表格字段行可标 NO_BREAK。
- 如果评价检索单元边界，独立记录、API 参数行和数据库字段行可以合理切分。

不应在同一 Boundary F1 中混用这两种目标。

### 应删除或单独标记的噪声候选

以下候选主要是封面日期、签字、修订历史或会议元数据，不适合直接参与语义分块评价：

- P01：`BP001`、`BP009`、`BP034`、`BP041`、`BP053`、`BP056`
- P02：`BP010`、`BP022`、`BP027`、`BP030`、`BP031`、`BP032`、`BP033`
- P03：`BP001`、`BP009`、`BP022`、`BP034`、`BP046`、`BP053`、`BP056`、`BP065`、`BP068`

这些候选更适合作为“噪声过滤”单独任务，而不是 BREAK/NO_BREAK 二分类样本。

### 基线比较的评价口径风险

候选边界定义在结构单元之间，而 fixed-size 和 recursive 方法可能在单元内部切分。当前边界评价只能识别块间或行间边界，无法公平表示单元内部的预测边界，因此会系统性偏向结构单元驱动的方法。

## 数据版本问题

P01 同时存在两条生成路径：

- `scripts/build_review_dataset.py`：包含一组更具体、偏人工设计的 P01 问题。
- `scripts/build_generic_review_dataset.py`：生成当前使用的 36 条模板化 P01/P02/P03 问题。

当前 `workbench/P01/qa_review_set.json` 来自通用生成路径。重新运行不同脚本可能覆盖标注集。正式复核前应锁定数据版本、生成脚本、审核状态和实验读取路径。

## 建议的人工复核顺序

### P0：实验继续使用前必须完成

1. 裁决 `P02/QA002` 和修正 `P03/QA003`。
2. 明确 Boundary F1 评价的是父块边界还是检索子块边界。
3. 禁止正式结果回退使用 `suggested_label`；没有人工标签时应停止评价。
4. 将表格 QA 的证据标到具体行，评价时使用行级证据。
5. 锁定标注集版本，避免生成脚本覆盖人工结果。

### P1：正式论文实验前完成

1. 人工改写 55 条泛化模板问题。
2. 删除或合并重复事实问题。
3. 对边界候选进行盲标，不向标注者展示 `suggested_label`。
4. 至少使用两名标注者，并报告一致性与仲裁规则。
5. 增加困难负例和同章节语义突变边界。
6. 对 URL、IP、人员、地点、电话等内容完成脱敏。

### P2：提高论文说服力

1. 每项目增加 QA 和边界样本量，并报告 bootstrap 置信区间。
2. 将开发集和最终测试集分离，避免使用测试集选择 v6 参数和父子权重。
3. 同时报告块级命中、行级命中和证据 span 命中。
4. 按问题类型分别报告结果，避免项目间类型分布差异掩盖真实效果。

## 推荐结论表述

在人工复核完成前，现有结果应表述为：

> 在自动生成并待人工复核的预标注集上，Proposed v6 展现出较好的探索性结果。由于边界标签与 QA 均存在规则生成偏差，且当前检索评价采用较宽松的块级证据匹配，结果不能直接视为人工金标准上的最终性能。
