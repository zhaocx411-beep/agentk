# Repository rules

DO NOT EDIT THIS FILE. These rules are set by the repository owner and are not open to revision, extension, or "clarification" by contributors or their tools. The only person who edits this file is the owner, acting deliberately; if you are not certain that describes you, it does not.

These rules are not a development guide. An exception to any rule requires the owner's explicit approval in a merge request.

## Repository content

Do not add documentation directories or files. Do not update existing documentation, including README and CHANGELOG, unless explicitly requested by the owner. Code changes and completed verification do not authorize documentation changes.

Text that enters the repository (code, comments, documentation, commit messages) describes only facts about the repository itself. Plans, notes, design memos, release sequencing, verification records, and coordination with other repositories stay outside the repository, in any location and format.

## Code comments

Do not narrate the code. Comments that repeat names, types, control flow, execution steps, or test assertions have no place here. Do not add boilerplate doc comments merely because a symbol is exported.

A comment is allowed only to explain a local mechanism, API contract, or external constraint that the code cannot make clear. State the necessary fact briefly, next to the relevant code, and only once.

Do not put architecture, design decisions, business policies, historical rationale, rejected alternatives, or future plans in comments. This applies to source code, protocols, SQL, configuration, and tests.

## Code layout

Code is written to be read. Lay it out the way a careful human would, in every language and file type in this repository: Go, Python, shell, Dockerfiles, YAML, and configuration alike. A formatter only normalizes whitespace. It does not make dense code readable, and running one excuses neither the layout it was given nor the layout it produced.

Do not compress code onto one line. Do not chain statements with semicolons, do not pack a multi-statement body into a one-line closure, block, or shell group, and do not let a call, literal, command, or list run on until the formatter or the edge of the screen breaks it. When something is long, break it yourself where the meaning divides, and keep together what belongs together. Short, simple constructs, such as a small map or a single-condition guard, stay on one line.

Separate top-level declarations with a blank line, and separate the logical steps inside a function the same way.

## Tests

Implementation and tests are two separate tasks. A task that implements or changes behavior delivers the implementation only: it does not add or modify tests, and it is not considered complete because tests were written. If the implementation breaks existing tests, the task is delivered with those failures reported, not repaired; fixing them is a separate task. Tests are written only in a separate task that is explicitly requested for that purpose. Finishing an implementation, passing verification, or being asked about coverage does not start that task.

Do not work test-first. Do not write a failing test before the implementation, do not interleave tests with implementation, and do not let tests decide the shape of the code. Do not add interfaces, injection points, exported helpers, fakes, or configuration whose only purpose is to make code testable.

A test exists only to protect something a reviewer can name: a public contract, a cross-language guarantee, a non-obvious edge case, or a failure mode that has actually occurred. Tests that restate the implementation, assert on mocks, calls, or internal structure, pin incidental behavior, or exist to raise coverage are not accepted.
